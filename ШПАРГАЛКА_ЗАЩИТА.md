## ИНТЕРФЕЙС И ПЛАТФОРМА

### WPF — Windows Presentation Foundation
Фреймворк от Microsoft для создания desktop-приложений на Windows.
Использует XAML (язык разметки) для описания интерфейса — как HTML, но для десктопа.
**Почему WPF?** Нативное Windows-приложение, богатый UI, поддержка тем и анимаций.
В проекте: весь клиент — заметки, Kanban, контакты, настройки.

### Web API / ASP.NET Core
Серверное приложение, которое принимает HTTP-запросы и возвращает данные в формате JSON.
Клиент (WPF) отправляет запрос → сервер обрабатывает → возвращает ответ.
**Пример:** клиент хочет получить заметки → GET /api/v1/notes → сервер достаёт из БД → возвращает JSON.
В проекте: корпоративный режим, все данные идут через сервер.

### REST / HTTP методы
- GET — получить данные
- POST — создать
- PUT — обновить
- DELETE — удалить
- PATCH — частичное обновление (например, только переместить задачу)

## АРХИТЕКТУРА

### Clean Architecture (Чистая архитектура)
Принцип разделения кода на слои, где внутренние слои не зависят от внешних.
```
[Интерфейс] → [Бизнес-логика] → [Безопасность/Инфраструктура] → [БД]
```
**Зачем?** Можно заменить базу данных или интерфейс, не трогая бизнес-логику.
Можно тестировать каждый слой отдельно.

### CQRS — Command Query Responsibility Segregation
Расшифровка: «Разделение ответственности команд и запросов».

**Идея:** любое действие в системе — это либо:
- **Command** (команда) — что-то меняет: создать заметку, удалить задачу, войти в систему
- **Query** (запрос) — только читает, ничего не меняет: получить список заметок, проверить аудит

**Как работает в проекте:**
1. Пользователь нажимает «Создать заметку»
2. ViewModel создаёт `CreateNoteCommand` с данными
3. MediatR находит нужный обработчик (`CreateNoteCommandHandler`)
4. Обработчик шифрует данные, сохраняет в БД, записывает в аудит
5. Возвращает результат

**Зачем разделять?** Чтение и запись имеют разные требования — безопасность, кэширование, производительность.

### MediatR
Библиотека-посредник. Реализует паттерн «Медиатор».
Вместо того чтобы ViewModel напрямую вызывал репозиторий → ViewModel отправляет команду в MediatR → MediatR сам находит нужный обработчик.
**Зачем?** ViewModel не знает, кто обработает команду. Слои не связаны напрямую.

### Dependency Injection (DI) — Внедрение зависимостей
Объекты не создают свои зависимости сами — получают их снаружи.
**Пример:** обработчик команды не создаёт `new GostCryptoService()` — получает его через конструктор.
Это позволяет на тестах подменить реальный сервис на «фиктивный» (mock).

### Entity Framework Core (EF Core)
ORM — Object-Relational Mapper. Позволяет работать с базой данных через C#-объекты, без написания SQL вручную.
```csharp
// Вместо SQL: SELECT * FROM notes WHERE user_id = '...'
var notes = await db.Notes.Where(n => n.UserId == userId).ToListAsync();
```

## КРИПТОГРАФИЯ (САМОЕ ВАЖНОЕ)

### ГОСТ Р 34.12-2015 «Кузнечик» — шифрование данных
**Что это:** российский стандарт блочного шифрования, принят в 2015 году.
**Параметры:**
- Блок: **128 бит** (16 байт) — данные шифруются порциями по 16 байт
- Ключ: **256 бит** (32 байта)
- Режим в проекте: **CTR** (Counter Mode — режим счётчика)

**Как работает CTR режим:**
Не шифрует данные напрямую. Шифрует последовательные значения счётчика → получает «гамму» (псевдослучайную последовательность) → XOR гаммы с открытым текстом = шифртекст.
Плюс CTR: можно шифровать данные любой длины, не кратной 16 байтам.

**Nonce (одноразовый вектор):**
128-битное случайное число, уникальное для каждой записи. Хранится рядом с шифртекстом.
Зачем: одни и те же данные с разными nonce дают разный шифртекст.

**В проекте:** каждая заметка, задача, контакт — шифруются Кузнечиком. Ключ разный у каждого пользователя.

---

### ГОСТ Р 34.11-2012 «Стрибог» — хеш-функция
**Что это:** российский стандарт хеширования, принят в 2012 году.
**Параметры:**
- Стрибог-256: выход **256 бит** (32 байта)
- Стрибог-512: выход **512 бит** (64 байта)

**Что такое хеш:** односторонняя функция. Любые данные → строка фиксированной длины.
Изменишь хоть один байт входных данных → хеш полностью изменится.
Восстановить данные из хеша — невозможно.

**Где используется Стрибог в проекте:**
1. **Хеш-цепочка аудита** — каждая запись журнала хешируется Стрибог-256
2. **PBKDF2** — как внутренняя PRF-функция при выводе ключа из пароля
3. **Отпечаток устройства** — Стрибог-256 от характеристик железа
4. **Хеш refresh-токена** — в БД хранится не сам токен, а его хеш

---

### HMAC — контроль целостности
**Расшифровка:** Hash-based Message Authentication Code — имитовставка на основе хеша.

**Простыми словами:** подпись на данных. Доказывает что данные не изменились.

**Формула:** `HMAC = Стрибог-256(hmacKey || данные)`

**Где используется:**
- После шифрования каждой записи вычисляется HMAC от (nonce + шифртекст)
- При чтении — сначала проверяется HMAC, и только если совпал — расшифровывается
- Если кто-то изменил шифртекст в БД → HMAC не совпадёт → данные не расшифруются → система выбросит ошибку

**Схема Encrypt-then-MAC:**
```
Открытый текст
    ↓ Кузнечик CTR + nonce
Шифртекст
    ↓ HMAC-Стрибог(hmacKey, nonce || шифртекст)
HMAC (32 байта)
```
При чтении: сначала проверить HMAC → потом расшифровать.

---

### PBKDF2 — вывод ключа из пароля
**Расшифровка:** Password-Based Key Derivation Function 2.

**Зачем:** пароль пользователя — слабый (короткий, предсказуемый). Нельзя использовать его напрямую как ключ шифрования.

**Как работает:**
1. Берём пароль + случайная соль (32 байта)
2. Прогоняем через хеш-функцию **100 000 раз**
3. Получаем 64 байта:
   - Первые 32 байта → ключ шифрования (для Кузнечика)
   - Вторые 32 байта → ключ HMAC (для Стрибога)

**Зачем 100 000 итераций:** замедляет перебор паролей в 100 000 раз. Хакер вместо 1 млн проверок/сек получает ~10.

**Соль:** случайные 32 байта, уникальные для каждого пользователя. Хранится в БД рядом с хешем. Исключает атаку по радужным таблицам.

---

### JWT — токен авторизации
**Расшифровка:** JSON Web Token.

**Что это:** строка из трёх частей, разделённых точками: заголовок.данные.подпись.

**Что хранится в токене (claims):**
- userId, role, device_id, session_id, время жизни

**Как работает:**
1. Пользователь входит → сервер выдаёт access_token (60 мин) + refresh_token (7 дней)
2. Каждый запрос к API → клиент добавляет заголовок `Authorization: Bearer <токен>`
3. Сервер проверяет подпись токена → доверяет данным внутри

**Access vs Refresh:**
- Access token — короткий (60 мин), для запросов к API
- Refresh token — длинный (7 дней), только для получения нового access token
- В БД хранится не сам refresh token, а его Стрибог-256 хеш

## БЕЗОПАСНОСТЬ

### RBAC — ролевая модель доступа
**Расшифровка:** Role-Based Access Control.

**4 роли в проекте:**
| Роль | Что может |
|------|-----------|
| User | Создавать/редактировать свои заметки, задачи, контакты |
| Manager | То же + видеть данные подчинённых |
| Auditor | Только читать журнал аудита |
| Admin | Полный доступ + управление пользователями |

**Как реализовано:** при каждом запросе MediatR-поведение проверяет роль пользователя. Нет права → HTTP 403 Forbidden.

---

### Хеш-цепочка аудита
**Зачем:** обычный журнал можно тихо подправить. Цепочка хешей делает это невозможным.

**Формула каждой записи:**
```
CurrentHash = Стрибог-256(PrevHash || timestamp_мс || action || entityId || userId)
```
Первая запись: PrevHash = 32 нулевых байта.

**Проверка:** система пересчитывает все хеши с нуля. Если хоть одна запись изменена — хеш не совпадёт — система покажет номер записи с вмешательством.

**В интерфейсе:** кнопка «Проверить целостность» → зелёный баннер «Цепочка не нарушена» или красный «Вмешательство в запись #N».

---

### Device Fingerprint — привязка к устройству
**Что это:** уникальный «отпечаток» компьютера.

**Как вычисляется:**
```
CPU ProcessorId + Disk SerialNumber + BIOS SerialNumber
          ↓ Стрибог-256
        Base64-строка (44 символа)
```
Читается через WMI (Windows Management Instrumentation) — системный интерфейс Windows.

**Как работает защита:**
- При первом входе отпечаток сохраняется в профиль пользователя
- При каждом входе — сравнивается с сохранённым
- Не совпал → вход заблокирован, даже если пароль верный
- Каждый API-запрос содержит отпечаток в заголовке `X-Device-Fingerprint`

### STRIDE — модель угроз
**Расшифровка:** Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege.

**Что это:** методология анализа угроз безопасности. Каждая буква — тип атаки:

| Буква | Угроза | Как защищаемся |
|-------|--------|----------------|
| S — Spoofing | Подмена личности | JWT + device fingerprint |
| T — Tampering | Изменение данных | HMAC на шифртексте, хеш-цепочка |
| R — Repudiation | Отрицание действий | Журнал аудита с цепочкой |
| I — Information Disclosure | Утечка данных | ГОСТ-шифрование всех записей |
| D — Denial of Service | Отказ в обслуживании | Rate limiting (5 попыток/мин) |
| E — Elevation of Privilege | Повышение привилегий | RBAC + проверка на каждом запросе |

## РЕАЛЬНОЕ ВРЕМЯ

### SignalR
Библиотека от Microsoft для двустороннего общения сервер ↔ клиент в реальном времени.

**Обычный HTTP:** клиент спрашивает → сервер отвечает. Сервер сам не может ничего отправить.
**SignalR:** сервер может отправить сообщение клиенту в любой момент.

**Как работает (упрощённо):** устанавливается постоянное WebSocket-соединение между клиентом и сервером.

**В проекте:**
- Когда один пользователь перетаскивает задачу в Kanban → сервер через SignalR уведомляет остальных → их доски обновляются без перезагрузки
- Уведомление «Заметка будет уничтожена через 30 минут»

## ТЕСТИРОВАНИЕ

### Что такое автотесты
Программы, которые проверяют другие программы. Запускаются автоматически, без участия человека.

**Виды тестов в проекте:**

**Unit-тесты (модульные)** — тестируют один класс/метод изолированно.
Зависимости заменяются на «моки» (заглушки).
Пример: проверить что `LoginCommandHandler` блокирует пользователя после 5 неверных паролей.

**Интеграционные тесты** — тестируют несколько компонентов вместе.
Пример: отправить HTTP-запрос к реальному контроллеру, проверить что вернулся правильный JSON.

**Тест-векторы ГОСТ** — официальные эталонные данные из стандарта.
Пример: «если зашифровать эти конкретные 16 байт этим конкретным ключом — должно получиться вот это».
Проверяет что реализация алгоритма точно соответствует стандарту, а не «как-то работает».

**Структура 41 теста:**
| Набор | Кол-во | Что тестирует |
|-------|--------|---------------|
| Domain | 1 | Базовые инварианты сущностей |
| Application | 10 | CQRS-обработчики (логин, блокировка, RBAC) |
| Infrastructure | 22 | Криптография по ГОСТ-векторам, хеш-цепочка |
| Server | 8 | HTTP-эндпоинты, JWT, коды ответов |

**xUnit** — фреймворк для написания тестов на C#.
**WebApplicationFactory** — поднимает реальный ASP.NET Core сервер в памяти для интеграционных тестов.
**Mock (Moq)** — подмена зависимостей. Вместо реальной БД — объект-заглушка.

## БАЗА ДАННЫХ

### Microsoft SQL Server / LocalDB
**SQL Server** — полноценная СУБД для корпоративного режима.
**LocalDB** — облегчённая версия SQL Server, устанавливается автоматически, для персонального режима. Не нужен отдельный сервер.

### Почему данные в БД нечитаемы без ключа
В таблице `notes` столбец `content_encrypted` имеет тип `VARBINARY(MAX)` — бинарные данные.
Даже если злоумышленник получит прямой доступ к SQL Server — он увидит только случайные байты.
Ключ нигде в БД не хранится. Он выводится из пароля пользователя через PBKDF2 каждый раз при входе.

## ЧАСТЫЕ ВОПРОСЫ КОМИССИИ

**Q: Чем отличается от обычного Evernote?**
A: Evernote хранит данные в открытом виде на зарубежных серверах. ConSecOrg шифрует каждую запись по российскому стандарту — без ключа данные нечитаемы даже для администратора сервера.

**Q: Что если злоумышленник украдёт базу данных?**
A: Он получит зашифрованные бинарные данные. Ключ шифрования не хранится в БД — он выводится из пароля пользователя. Без пароля расшифровать невозможно.

**Q: Что если злоумышленник узнает пароль но использует другой компьютер?**
A: Система проверяет отпечаток устройства при каждом входе. Другой компьютер → DeviceMismatchException → вход заблокирован.

**Q: Как доказать что алгоритмы реализованы правильно?**
A: 22 теста в Infrastructure.Tests используют официальные тест-векторы из ГОСТ Р 34.12-2015 и ГОСТ Р 34.11-2012. Если хоть один байт не совпадёт с эталоном — тест упадёт.

**Q: Что такое хеш-цепочка простыми словами?**
A: Как блокчейн в Биткоине — каждый блок содержит хеш предыдущего. Изменить один блок в середине — невозможно незаметно, потому что все последующие блоки станут недействительными.

**Q: Почему CTR режим, а не CBC?**
A: CTR позволяет шифровать данные произвольной длины без дополнения (padding). Также позволяет параллельное шифрование. CBC уязвим к padding oracle атакам при неправильной реализации.

**Q: Что такое BouncyCastle?**
A: Открытая криптографическая библиотека для .NET. Реализует российские алгоритмы ГОСТ, которые не входят в стандартную библиотеку .NET. Используется в проекте для Кузнечика и Стрибога.

**Q: Как работает двухрежимность?**
A: При старте приложения выбирается режим. Персональный — все сервисы работают с локальной БД через EF Core напрямую. Корпоративный — сервисы обращаются к HTTP API. Переключение пересоздаёт DI-контейнер.

**Q: Что такое Kanban?**
A: Метод управления задачами. Задачи — карточки, которые перемещаются между колонками: «К выполнению» → «В работе» → «На проверке» → «Готово». Визуально показывает состояние всех задач.

**Q: Как работает таймер уничтожения заметок?**
A: Пользователь задаёт дату/время. Фоновый сервис каждые 60 секунд проверяет заметки с истёкшим временем. При истечении — перезаписывает зашифрованные данные случайными байтами в БД, затем удаляет запись. Это гарантирует что данные нельзя восстановить из дискового пространства.
